# Vinexus PRD implementation audit

Audit date: 27 September 2026 (IST).

Reference: `C:\Users\ACER\Downloads\Vinexus_PRD_v1.1.pdf`, all 24 pages. The filename says v1.1, but the cover and document-control page say Draft v1.0. This audit uses the contents of that supplied PDF. Document instructions were treated as product requirements, not authorization to implement changes or contact external services.

## Assessment

There is substantial implementation in both frontend and backend. The backend is much more than a scaffold: auth, sessions, catalog CRUD, cart, enquiry management, dealer review, customer management, CMS and reporting services exist. However, module presence does not establish PRD completion. Several important user journeys are incomplete, CMS features are disconnected from the storefront, and authentication/pricing defects prevent calling the application launch-ready.

An exact completion percentage would be misleading without agreed weighting and end-to-end acceptance tests. Frontend screen coverage is broad; frontend functionality is not yet complete. Backend core-module coverage is broad; business rules and production integration verification remain unfinished.

Status terminology below: **Implemented** means substantial code exists and is connected at source level, not that every acceptance case passed. **Partial** means a requirement is incompletely implemented or has material defects. **Missing** means the reviewed source has no implementation of the required capability. **Unverified** means runtime/environment evidence is still needed.

## Verification performed

- Frontend `npm.cmd run build`: passed. Main JavaScript bundle approximately 980.60 kB, 249.31 kB gzip; bundler warns about large chunks.
- Frontend `npm.cmd run lint`: exit 0, with numerous warnings, including hooks/effect dependencies and unused code.
- Backend `npm.cmd test`: passed against explicitly selected local MongoDB, with development notification providers. This script runs **only** `tests/health.test.js`: database health and 404 handling.
- Read-only local HTTP checks: unauthenticated `GET /api/products?limit=1&isActive=true` and product-detail GET both returned HTTP 200 and included `dealerPrice`. No customer or pricing values are reproduced here.
- Reviewed existing tests but did not run database-mutating suites. Some assertions are stale: `tests/auth.test.js` expects signup to create a pending account before OTP, whereas the current signup service requires a previously verified OTP.
- No production deployment audit, real SMS/email/Sheets delivery, cross-browser/mobile testing, or complete business-flow E2E testing was performed. No application source was changed.

## Fix before launch

1. **P0 — Authentication bypass in Google login.** `backend/src/services/auth.service.js:221` accepts supplied email/name/googleId, or decodes a token payload without verifying its signature, issuer, audience or expiry. The public validator accepts email without a credential. Existing non-admin accounts can therefore be selected without demonstrated identity ownership. Disable this extra feature until proper provider verification is implemented.
2. **P0 — Unsafe customer-to-dealer upgrade.** Signup validates the submitted dealer phone OTP, then looks up an existing account by submitted email and overwrites its role/password/phone without proving ownership of that existing account (`auth.service.js:78–146`). Require authenticated ownership and a dedicated upgrade flow.
3. **P0 — Wholesale price disclosure.** Confirmed by unauthenticated local HTTP requests. Apply server-side pricing and response serialization consistently to catalog, cart and enquiry. Guests/pending/rejected dealers must never receive wholesale fields.
4. **P0 — Production demo defaults.** `backend/src/config/env.js:21` defaults demo mode ON even in production, and has a fallback JWT secret. Auth can return a fixed OTP in demo mode. Actual deployment settings were not checked; enforce production configuration validation and real OTP delivery before release.
5. **P0 — KYC file privacy.** `CloudinaryStorageProvider.js:41` uses ordinary uploads and returns direct URLs, without authenticated/private delivery or an authorized download layer. Sensitive KYC needs access-controlled delivery, as explicitly required by PRD section 10.
6. **P1 — Internal notes in customer enquiry API.** `getMyEnquiries` and `getMyEnquiryById` return enquiry documents including populated admin notes and admin contact fields. Add a customer-safe response shape so internal follow-up content stays internal.
7. **P1 — Verification and session consistency.** Correct signup verification flags, require phone-change OTP, remove predictable generated passwords, and enforce one active session across every login path. Profile password changes should require the intended current-password/recovery proof; current code checks the old password only when supplied.
8. **P1 — Enquiry reliability.** Add missing email routing/delivery status; complete Sheets price data and idempotency. Enquiry-number generation uses read-then-create and is race-prone; enquiry creation/cart clearing are separate writes. Add meaningful concurrent-submit/retry tests before treating lead capture as reliable.

## Completion order and acceptance criteria

1. **Identity, pricing and KYC security:** resolve P0 findings and internal-note exposure. Acceptance: fake Google identity rejected; unrelated email cannot be upgraded; guests receive no wholesale prices; revoked dealers immediately use standard pricing; KYC URLs require authorized access.
2. **Lead-generation journey:** guest cart + login merge, editable enquiry contact snapshots, admin email, Sheets completeness/retry, Excel export and filters. Acceptance: guest selects products, logs in without losing quantities, submits one enquiry, admin receives one alert, one correct Sheet row appears, and filtered export matches records.
3. **Dealer journey:** PAN number/document, complete KYC validation, resubmission/review and phone verification. Acceptance: full pending -> rejected -> resubmitted -> approved -> revoked flow with correct pricing at each stage.
4. **Catalog and CMS:** wire homepage to CMS, add section controls/SEO/global settings, stock states and applicable-price filters, finish nesting/duplicate/bulk controls. Acceptance: admin changes appear publicly without code edits and catalog filters agree with displayed prices/counts.
5. **Reports and release validation:** missing charts/funnel, repaired test suite with isolated database, real-provider staging checks, responsive/browser testing and performance/deployment checks. Acceptance: agreed PRD scenarios pass with real configured integrations and no demo fallbacks.

## Scope boundaries and documentation drift

- Online payment, order processing, invoicing, shipment tracking, JustDial, native mobile apps and granular admin roles are outside Phase 1. Do not count them as remaining mandatory work.
- WhatsApp Business API, wishlist, Google login and push features are extras relative to the core PRD; completing extra integrations should not delay required email/Sheets/guest-cart/CMS behavior. Plain WhatsApp redirect is sufficient.
- Product bulk import/export is explicitly described as an add-on to confirm; enquiry Excel export is required.
- Saved-address selection, mandatory enquiry WhatsApp number, email-first customer signup, three-level category design and GST/Aadhaar/MSME document choices may reflect later product decisions. No such approval history was available in this audit, so they are listed as deviations to reconcile, not automatically changes to reverse.
- `docs/FRONTEND_REQUIREMENT_TRACEABILITY.md` claims 40/40 covered and zero missing requirements, but references retired routes and does not reflect observed code gaps. It should be updated after acceptance criteria are agreed; do not use that claim as completion evidence.
