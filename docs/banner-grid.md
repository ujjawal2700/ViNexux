# Homepage bento banners

Open **Admin → Homepage Banners** (`/admin/cms/banners`). The **Homepage bento grid** editor contains two fixed sections, with up to five images in each section (10 images total). Select multiple PNG/JPG/WebP files at once, each up to 5 MB, adjust each image in the preview dialog, then confirm Upload. Nothing is uploaded until confirmed. Confirmed uploads save directly to the homepage; there is no separate publish step for this CMS feature.

**Preview / crop & adjust** opens the same editor for existing banners without requiring a new upload. Choose fill/crop or fit-entire-artwork mode, zoom (1×–3×), and horizontal/vertical position (0–100%). Drag the highlighted tile or use the keyboard-accessible sliders. Desktop/tablet/mobile previews show both tiles together, and **View original image** shows the unframed source. Cropping is non-destructive: original pixels remain stored, while bounded framing metadata controls the visible region. Preview and storefront use the same rendering helper. The crop applies across devices; responsive tile proportions can show a different amount of the image, so check each device. Reset crop restores centered 1× framing in the draft dialog; Cancel discards dialog changes. Save crop & adjustments updates the live banner. The expandable **Preview homepage grid** also shows the saved two-section layout.

Layout: a wide horizontal banner uses the original first and middle columns, with a tall vertical banner on the right. Both banners stay side by side on smaller screens. Corners are subtly rounded (10 px desktop, 8 px mobile). The old single full-width hero carousel is no longer rendered.

Use landscape artwork (2700 × 1200 px, approximately 9:4) for section 1 and portrait artwork (900 × 1200 px, 3:4) for section 2. The right tile keeps a 3:4 aspect ratio on desktop, tablet and mobile. Its height sets the row height; the horizontal tile fills the remaining width. Each image can be set to **Show entire image** instead of **Fill tile**. Optional captions and destination links are independently editable. Replacement works even when a section already has five images. Remove only removes the placement; original stored uploads are retained.

Each section rotates independently when it has multiple images. In each section, set **Automatically change banner every (seconds)** to 1–120 seconds (including tenths of a second) and click **Save rotation time**. Each saved time applies only to that section, including sections containing videos; the carousel advances on the configured timer rather than waiting for a video to finish. Existing sections keep their original 5-second / 5.7-second timings until changed. Previous/next controls are available. Autoplay pauses on hover, keyboard focus and when the document is hidden; reduced-motion preferences disable autoplay and fades. Static one-image sections do not show carousel controls.

Before the first dedicated-grid upload, both sections show collection links. Only images uploaded into the corresponding section appear there. Seasonal-theme previews use the same bento grid. The old banner library, its full-width fallback, and per-campaign legacy banner selection have been removed from the admin workflow and storefront; previously stored `Banner` documents and their image files are retained but no longer rendered by the site.

## Backend and deployment

The `BannerGrid` singleton stores exactly two sections with embedded image metadata. Authenticated admin endpoints live under `/api/admin/cms/banner-grid`; the public read endpoint is `/api/content/banner-grid` with `Cache-Control: no-store`. Writes use an optimistic revision and atomic capacity checks, so stale tabs and simultaneous uploads cannot exceed five images in a section. Refresh the grid after a conflict.

Cloudinary uses the existing CMS storage pipeline. Development storage writes real decoded WebP files to `backend/var/theme-assets/`, served by the existing public theme-asset endpoint; keep this directory on persistent storage for deployed development-provider installations. Replaced/removed uploads are retained; orphan-file cleanup is not included. Older four-section grids display their first and fourth sections immediately. On the first admin request, the grid is upgraded atomically to those two sections and its revision advances; artwork, transitions, framing and original uploaded files are preserved for the retained sections. Middle placements are removed. Deploy both frontend and backend; no live production data is modified by the source changes.

Tests: `tests/unit/bannerGrid.test.js`, `tests/api/bannerGrid.api.test.js`, and `tests/e2e/bannerGrid.spec.js`. Existing seasonal-theme tests also cover preview/activation and footer behavior with the new hero layout.

## Promotional videos in either banner

Both horizontal and vertical sections accept a mixture of images and videos, retaining the existing limit of five placements per section. Upload PNG/JPG/WebP/SVG images up to 5 MB, or MP4/WebM/MOV videos up to 50 MB and 60 seconds. Cropping and destination links apply to either media type. Video source dimensions must not exceed 4096 pixels per edge. The admin can preview a local video before confirming its upload.

The server validates the video container and probes duration/dimensions before encoding. A single bounded encoder job converts it to a muted H.264 MP4, maximum 1280 pixels per edge at 24 fps, with a 1.4 Mbps maximum bitrate and fast-start metadata. A separate WebP poster is generated. Only the optimized files are sent to Cloudinary, using the **video** resource type for MP4 and **image** for the poster. Temporary source/encoded files are removed in a finally block. Concurrent optimization requests receive a retryable busy response, keeping upload work bounded; they do not block the Node event loop. Failed or conflicting placement saves discard their new uploaded assets. Removing an established placement continues to retain its original stored media, as before.

The frontend initially renders a poster and a video element with `preload="none"` and no `src`. It requests no video bytes until a slide is active, visible, the tab is visible, the page has loaded, and a suitable connection has remained stable for three seconds. Automatic playback requires Network Information API reporting 4g, at least 2.5 Mbps, RTT no more than 300 ms, data saver off, and reduced motion off. Unknown or slow connections retain the poster with an explicit Play control. A visitor can request playback manually. Network degradation, hidden/inactive slides and prolonged buffering stop loading and return to the poster; no polling or repeated automatic retries are used. A later network-change signal can qualify playback again. Posters and images for inactive, unvisited slides are deferred.

Deployment uses `ffmpeg-static` and `ffprobe-static`; install the updated backend lockfile on the target server so platform binaries are present. `ffmpeg-static@5.3.0` is explicitly approved in npm's `allowScripts` configuration. `FFMPEG_PATH` and `FFPROBE_PATH` can override the packaged tools. These are optional configuration paths, not new credentials. Development media files are served with byte-range support from the existing immutable local asset route.

Public categories, banner metadata and footer content share short-lived requests between page/layout consumers; successful admin mutations invalidate these caches. Customer carts, account responses and product prices are never placed in this public cache. Homepage merchandising starts with 16 products per section instead of fetching every catalog page; View all links retain access to the complete flagged collections. Banner metadata loads independently of those catalog requests. Measured request counts and network-gating tests are in `tests/e2e/bannerVideo.spec.js`; actual site response time still depends on hosting, database latency, device and connection.
